1. PROJECT OVERVIEW & IDENTITY
================================================================================

Name:       Clyra AI (codenamed "Clyra AI Final")
Type:       Local-first AI desktop workspace application
GitHub:     https://github.com/Redlook096/Clyra-AI-Final
License:    ISC (code), parts Apache-2.0
App ID:     ai.clyra.desktop

Clyra AI is an all-in-one AI assistant that provides:
- Chat with streaming LLM responses (DeepSeek by default)
- Vibe Coder — AI code generation with live preview
- AI Clipper — AI video clipping and social publishing
- Web Browser — Built-in managed Chromium browser with AI agent control
- Creator Studio — Fake Text Stories, Would You Rather, Story Videos
- Study Pal — Source-grounded study tools (quiz, flashcards, notes)
- Voice Calls — Real-time voice assistant with STT/TTS
- Dictation — System-wide voice dictation
- OpenPencil — AI-powered design canvas
- Google Workspace integration (Gmail, Drive, etc.)

The app runs as a web app (via server.ts + Vite) OR as an Electron desktop
app. The Electron shell provides native Chromium browser tabs, dictation
overlay, and system-level integration.

2. TECH STACK SUMMARY
================================================================================

FRONTEND
- React 19 (with TypeScript)
- Vite 6 (bundler with HMR)
- Tailwind CSS 4 (via @tailwindcss/vite plugin)
- motion/react (Framer Motion successor) for animations
- GSAP for advanced animations
- Lucide React for icons
- Radix UI (dropdown-menu, progress, icons)
- Monaco Editor (@monaco-editor/react) for code editing
- XYFlow (@xyflow/react) for node graphs
- react-markdown + remark-gfm for rendering
- react-syntax-highlighter for code highlighting
- marked for Markdown parsing
- clsx + tailwind-merge for className utilities

BACKEND (Node.js / TypeScript)
- Express HTTP server with Vite middleware
- WebSocket (ws package) for voice streaming
- tsx for running TypeScript directly
- esbuild for server bundling
- Electron 43 for desktop shell
- electron-builder for packaging

LLM INTEGRATION
- OpenAI-compatible API (DeepSeek by default)
- @cline/sdk / cline for Cline coding agent
- @openhands/typescript-client for OpenHands (legacy M1)
- @opencode-ai/sdk for OpenCode integration

VOICE PIPELINE (Python)
- FastAPI + Uvicorn (HTTP + WebSocket server)
- Faster-Whisper for STT (speech-to-text)
- Chatterbox-Turbo for TTS (text-to-speech)
- Silero VAD for voice activity detection
- LiveKit for optional WebRTC transport
- Torch, NumPy, librosa, transformers, diffusers

TESTING
- Playwright for browser/E2E testing
- tsx for TypeScript test scripts

DESKTOP
- Electron with native Chromium WebContentsView
- Native OSA/dictation integration

OVERALL DATA FLOW:
  1. User types message → React ChatComposer → App.tsx calls API
  2. API routes through server.ts → proxies to DeepSeek API
  3. LLM response streams back via SSE → App.tsx parses & renders
  4. For voice: Mic PCM16 → WebSocket → Python STT → text → LLM → TTS → audio back
  5. For Vibe Coder: User prompt → LLM generates structured tokens → parser
     extracts code → files saved → preview server starts → iframe renders
  6. For managed browser: User URL → server.ts → Playwright CDP → Chromium

7. MAIN SERVER (server.ts) — EVERY API ENDPOINT
================================================================================

server.ts is the central backend of Clyra AI. It is an Express + Vite server
that handles all API routes, proxies LLM requests, manages previews, and
orchestrates all subsystems. Key subsystems:

----- HEALTH -----
  GET  /api/health
    → Returns { status: "ok" }

----- CHAT / LLM PROXY -----
  POST /api/clyra/chat
    → Proxies raw request body to DeepSeek (or configured endpoint)
    → Streams response body back to client
    → Requires DEEPSEEK_API_KEY in .env

  POST /api/deepseek/chat
    → Alias for /api/clyra/chat

  POST /api/openpencil/v1/chat/completions
    → OpenPencil LLM adapter — same proxy as chat
    → Used by OpenPencil design canvas to access Clyra's LLM

----- DICTATION -----
  POST /api/dictation/cleanup
    → Cleans up speech-to-text transcript using LLM
    → Parameters: transcript, level (raw/light/polished), dictionary[]
    → Fallback: conservative regex-based cleanup when no API key

  POST /api/dictation/optimise
    → Rewrites selected text based on spoken instruction
    → Parameters: selectedText, instruction
    → Fallback: conservative text optimisation

----- SMART TOOLBAR -----
  POST /api/smart-toolbar/action
    → Processes selected-text actions from native macOS toolbar
    → Parameters: text, instruction
    → Uses DeepSeek API with local fallback

----- CREATOR STUDIO -----
  POST /api/creator/generate
    → Generates scripts for: fake_text_story, story_video, would_rather
    → Parameters: kind, prompt, count, tone
    → Returns structured JSON from LLM (json_object mode)

  POST /api/creator/transcode
    → Transcodes WebM video to MP4 using FFmpeg
    → Parameters: fps (24-60), filename
    → Uses H.264 ultrafast with CRF 15, AAC audio
    → Output: downloadable MP4

----- STUDY PAL -----
  POST /api/study/fetch
    → Fetches and extracts text from a URL
    → Strips HTML, scripts, styles; extracts readable text
    → Blocks private network addresses

  POST /api/study/ask
    → Answers questions grounded in study sources
    → Modes: answer, summary, flashcards, quiz, plan
    → Citations inline as [S1], [S2] referencing sources

  POST /api/study/quiz
    → Generates practice quiz from topic and/or sources
    → JSON mode with 4-option multiple choice
    → Returns questions with hints and explanations

  POST /api/study/flashcards
    → Generates flashcards from topic and/or sources
    → JSON mode with front/back/tag structure

  POST /api/study/notes
    → Generates Cornell-method study notes
    → Sections with cues and key points
    → Self-test questions with model answers
    → Inline source citations

----- MANAGED BROWSER (Playwright) -----

  - A BrowserWindow with sandboxed WebContentsView for the UI

  - Native overlay surfaces (ChromiumSurfaceManager)

  - Deep Research pipeline (DeepResearchManager)

KEY ARCHITECTURAL DECISIONS:
  - All OAuth tokens/credentials stay in the main process, never over IPC
  - Sandboxed UI WebContentsView (contextIsolation, no nodeIntegration)
  - Background throttling disabled for dictation responsiveness
  - Separate browser profile (not system Chrome)
  - Browser bridge (HTTP server on loopback) for Renderer ↔ Browser communication
  - Permission handler allows microphone only for local origins

BOOT SEQUENCE:
  1. Start browser bridge HTTP server (port 9224)
  2. Start local Express service (spawns server.ts via tsx)
     - Development: tsx server.ts
     - Production: Electron binary with dist/server.js
  3. Wait for /api/health to respond (45s timeout)
  4. Create BrowserWindow with WebContentsView
  5. Initialize managers (browser, dictation, toolbar, Google, research, memory)
  6. Load http://127.0.0.1:{port} in WebContentsView
  7. Show window when page finishes loading

SHUTDOWN SEQUENCE:
  1. Destroy native managers
  2. Close browser bridge
  3. SIGTERM → local service → wait up to 8s → SIGKILL
  4. app.exit(0)

10. VOICE PIPELINE (Python / FastAPI)
================================================================================

Location: backend/voice-pipeline/
Runtime:  Python 3.11 venv (.venv-voice311)
Port:     8787

ARCHITECTURE:
  FastAPI app providing:
    1. REST endpoints for health, STT, TTS
    2. WebSocket endpoint for real-time streaming voice sessions

COMPONENTS:
  main.py         — FastAPI application, WebSocket handler, session management
  config.py       — Configuration (models, sample rates, voices)
  stt_stream.py   — Streaming speech-to-text using Faster-Whisper
  tts_stream.py   — Text-to-speech using Chatterbox-Turbo
  vad.py          — Voice Activity Detection using Silero VAD

MODELS USED:
  STT: Faster-Whisper (configurable model, default: tiny.en)
  TTS: Chatterbox-Turbo (persistent on-device synthesis)
  VAD: Silero VAD (fallback to energy-based detection)

REST ENDPOINTS:
  GET  /health
    → { status: "ok", stt_model, tts_voice, tts_engine, vad, ... }

  POST /stt
    → Convert base64 PCM16 audio to text
    → { audio: "base64...", sampleRate: 16000 }

  POST /tts
    → Convert text to base64 PCM16 audio
    → { text: "hello", voice: "Ryan", sampleRate: 44100 }

WEBSOCKET PROTOCOL (/stream):
  Client → Server:
    { type: "session_start", sessionId: "..." }
    { type: "audio", data: "base64..." }
    { type: "flush" }
    { type: "mute", muted: true/false }
    { type: "barge_in" }
    { type: "tts", text: "...", voice: "...", requestId: "..." }
    { type: "ping" }
    { type: "end" }

  Server → Client:
    { type: "ready", sessionId, sampleRate, sttModel, vad }
    { type: "transcript_partial", sessionId, text, confidence }
    { type: "transcript_final", sessionId, text, confidence, metrics }
    { type: "tts_chunk", sessionId, requestId, data, seq, codec: "pcm16" }
    { type: "tts_done", sessionId, requestId, metrics }
    { type: "barge_in", sessionId }
    { type: "pong" }
    { type: "error", message }

SESSION STATE:
  - Each WebSocket connection creates a SessionState
  - Audio worker thread for non-blocking transcription
  - Sender task for ordered WebSocket writes
  - Automatic model warmup on startup

TTS RUNTIME:
  - Single persistent Chatterbox-Turbo model shared by voice calls + creator narration
  - Remote Async Flash TTS available as alternative (via Node gateway)
  - Local pipeline TTS only warmed on startup with VOICE_PIPELINE_WARM_LOCAL_TTS=1

STARTUP:
  - Auto-started by server.ts if VOICE_ENABLED=true
  - Searches for Python venvs: .venv-voice311 > .venv-voice
  - Runs: python -m uvicorn main:app --host 127.0.0.1 --port 8787
  - Health check before spawning to avoid duplicates

12. VIBE CODER AGENT SYSTEM
================================================================================

The Vibe Coder uses a custom structured agent protocol with machine-readable

TOKEN DELIMITERS:
  <<<VIBE_THINKING>>>
    Agent reasoning/status block. Used for session reasoning, active agent
    name, phase, intent, context, TodoWrite snapshots, failure analysis,
    discoveries, and next tool decision.
    Structure:
      Build session
      Active agent: <Build|Plan|Explore|General|Scout>
      Phase: <Interpret|Discover|Design|Implement|Diagnose|Verify|Summarize>
      Intent: <what the user asked for>
      Context: <what is known from this session>
      TodoWrite: <short status list with one in-progress item>
      Next tool: <Read|Glob|Grep|Write|Edit|ApplyPatch|Bash|TodoWrite|Task|none>
      Why: <short reason>
    <<<END_VIBE_THINKING>>>

  <<<VIBE_ANALYZE path="vibe-project/...">>>
    Read existing generated files. Maps to Read/Glob/Grep tools.
    Rendered as stacked reading lines in UI.
    Only used for follow-up requests (existing files exist).
    <<<END_VIBE_ANALYZE>>>

  <<<VIBE_CODE file="vibe-project/..." added="N" removed="M">>>
    File write/edit/apply_patch output. Contains raw source code.
    One block per final file body.
    added = line count of the shipped file
    removed = lines removed (for edits)
    <<<END_VIBE_CODE>>>

  <<<VIBE_RUN>>>
    Shell command verification block.
    Shows command, purpose, and output.
    <<<END_VIBE_RUN>>>

AGENT ROLES (visible in thinking blocks):
  Build   — Default execution agent. Reads files, writes/edits code, verifies.
  Plan    — Used when user explicitly asks for planning or for complex design.
  Explore — Read-only project researcher for locating files and patterns.
  General — Broader reasoning for multi-step architecture and edge cases.
  Scout   — External/docs research agent for uncertain API/library usage.

OPERATIONAL ORDER:
  1. Interpret the product type and constraints
  2. Define complete product surface
  3. Create TodoWrite snapshot
  4. Form multi-file implementation map
  5. Write in dependency order
  6. Diagnose import/type/runtime risks
  7. Run verification
  8. Return final summary

  - All file paths must be under vibe-project/<project-folder>/
  - Cannot access or modify Clyra's own source tree
  - Live preview loads only from the sandbox namespace
  - Separate project folders prevent cross-contamination

  1. Observe current page (elements, text, headings)
  2. Send observation to LLM with task context
  3. LLM returns action + reasoning
  4. Validate action against safety rules

30. KEY DESIGN PATTERNS & CONVENTIONS
================================================================================

1. LOCAL-FIRST PRINCIPLE
   - All LLM API keys stay on the server, never sent to browser
   - Voice pipeline runs locally on device
   - Browser profiles are persistent and user-owned
   - Memory is file-backed and never sent to cloud

2. STREAMING ARCHITECTURE
   - Chat responses stream via SSE
   - Vibe agent output streams with custom token delimiters
   - Voice audio streams via WebSocket
   - Clipper pipeline streams via SSE
   - Deep research streams via SSE

3. SANDBOXED ISOLATION
   - Vibe projects isolated to specific directories
   - Sandbox paths cannot traverse out of project root
   - Managed browser blocks non-HTTP/HTTPS URLs
   - Page text is sanitized for prompt injection
   - No ../ traversal, no symlinks, no drive letters

4. FALLBACK STRATEGY
   - Dictation: conservative regex cleanup when LLM unavailable
   - Voice: Async Flash TTS when local pipeline unavailable
   - Chat: API key required; no fallback needed
   - Preview: Instant SVG placeholder, async PNG capture
   - Electron: Packaged Node fallback if Bun sidecar fails

5. COMPONENT PATTERNS
   - Lazy-loaded workspace components (React.lazy)
   - Tab-based workspace switching
   - AnimatePresence for enter/exit animations
   - motion/react for declarative animations
   - GSAP for advanced/cinematic animations

6. AGENT PATTERNS
   - Custom delimiter-based protocol for structured AI output
   - Token parser in the UI to render cards
   - Agent roles specified in thinking blocks
   - Tool mapping: Analyze→Read, Code→Write, Run→Bash
   - TodoWrite snapshots for task tracking within sessions

7. SECURITY PATTERNS
   - OAuth tokens NEVER cross IPC (Electron)
   - Renderer only sends command envelopes, not credentials
   - Browser permission handler restricts to local origins only
   - Prompt injection detection in page observations
   - Sensitive actions require user confirmation
   - High-impact browser actions blocked for agents
   - File paths sanitized aggressively (no path traversal)

8. PERSISTENCE PATTERNS
   - Browser: profile.json for history/bookmarks/downloads/settings
   - Projects: metadata.json + files/ + checkpoints/ + .agent/
   - Voice: session state in memory during call
   - Local memory: clyra-memory.dat (file-backed)
   - Chat: browser localStorage for conversations

9. ERROR HANDLING PATTERNS
   - All external API calls wrapped in try/catch with proper fallbacks
   - Streaming endpoints handle disconnect gracefully
   - Browser agent has recovery step for transient errors
   - Validation/fix loop (up to 5 retries)
   - Graceful shutdown with resource cleanup

10. NAMING CONVENTIONS
    - camelCase for variables, functions, components
    - PascalCase for React components, types, interfaces
    - kebab-case for file system, slugs, routes
    - snake_case for JSON schema fields (API compatibility)

FILE SYSTEM SAFETY:
  - All paths sanitized: no .. traversal, /../, null bytes
  - Sandbox root enforcement (path must resolve within sandbox)
  - Max path length enforced (96 chars per segment, 220 total)
  - Max file count (80 files per session)
  - Max file size (512 KB per file)
  - Blocked files: package.json, vite.config.*, tsconfig.json, .env*
  - Safe project ID characters only: [a-zA-Z0-9_-]

NETWORK SAFETY:
  - Study Pal blocks private/internal network addresses
  - Managed browser: only HTTP/HTTPS navigation
  - Origin checking on all CORS-enabled endpoints
  - Browser bridge authenticated with random token
  - IPC authorization checks sender identity

PROMPT INJECTION DEFENSE:
  - Page text scanned for instruction-like patterns
  - Suspicious lines removed from agent observation
  - Patterns detected: "ignore instructions", "reveal system prompt",
    "upload files", "mark task complete", "run shell command"
  - Dictation transcripts treated as untrusted data, never instructions
  - Selected text in smart toolbar treated as untrusted data

LLM SAFETY:
  - API keys never sent to browser (server-side only)
  - Response streaming proxied through server
  - Unified auth via single API key
  - Max token limits enforced on all LLM calls
  - Timeout limits on all external API calls

  - Sandboxed WebContentsView (no node integration)
  - Context isolation enabled
  - Web security enabled
  - Permission handler restricts microphone to local origins only
  - Google OAuth tokens never sent over IPC
  - Renderer IPC payloads validated for allowed fields only

  - Browser agent: wait ≤5s, keys ≤4, high-risk actions need confirmation
  - File deletions require user confirmation
  - Git destructive commands require approval
  - Project deletion requires metadata check first
  - Upload size limited (1.25 GB max)
  - Body size limit on Express (2 MB JSON)

DATA PRIVACY:
  - All data stored locally in Application Support directory
  - Browser profile isolated from system Chrome
