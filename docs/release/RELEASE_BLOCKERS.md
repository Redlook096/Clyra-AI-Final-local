## Vibe Coder — iOS/SwiftUI building removed (this pass, per explicit user request)

At the user's request, Vibe Coder's native iOS/SwiftUI app-building capability was removed entirely — no more offering to build native iOS apps, no more iOS Simulator preview, no more Xcode/xcodebuild integration. Web and desktop building are fully preserved and were re-verified live after the removal.

**Deleted outright** (all confirmed iOS-only via a repo-wide dependency check before deletion):
- `lib/mobile-platform-detect.ts`, `lib/iphone/**` (the full `/api/iphone/*` Express routes, the `xcrun simctl`/`xcodebuild` provider layer, the Windows↔Mac remote-pairing protocol).
- `src/components/clyra-code/{IPhonePanel,IPhoneSetupWizard,IPhoneInstallTerminal,ProjectExportPopover}.tsx`.
- `tools/clyra-iphone-cli.cjs`, `tools/iphone-e2e.mjs`, and the three `test:iphone:*` scripts in `package.json`.
- The bundled Apple/SwiftUI skill libraries: `lib/apple-skills-repo/`, `lib/claude-code-apple-skills/`, `lib/swiftui-agent-skill-repo/`, `lib/swiftui-design-skill/`, `skills/ios-swiftui/`, `skills/ios-design/` (some of these were stray git submodule gitlinks with no `.gitmodules` entry — cleaned up via `git rm --cached` + `rm -rf` on the working tree).

**Edited (iOS branches stripped, shared web/desktop logic kept)**: `server.ts`, `lib/opencode/opencode-routes.ts` (removed `IOS_AGENTS_MD`, the SwiftUI starter-scaffold generator, and the three call sites that triggered them), `lib/opencode/OpenCodeRuntimeManager.ts` (dropped the Swift-specific completion-validation regex and the "portable iOS guide" AGENTS.md upgrade guard), `store.ts`/`api.ts`/`RightPanel.tsx`/`VisualInspector.tsx`/`Sidebar.tsx` (dropped the `"ios"` platform union member and every branch keyed on it — iPhone-preview tab, the `__ios__` visual-edit sentinel, the Monaco Swift-completion branch, the sidebar's phone icon).

**A real bug was introduced and caught during this removal, worth recording as a process note**: an over-broad `sed` line-range deletion in `opencode-routes.ts` accidentally removed several **shared, non-iOS** helpers that happened to sit interleaved with the iOS-only code — `ensureProjectGitRepo`, `safeProjectId`, `projectPath`, `titleFor`, and the `MAX_PROMPT_LENGTH`/`MAX_ATTACHMENT_BYTES`/`subscriptions` constants. `npx tsc --noEmit -p .` reported **zero errors** throughout, which gave false confidence — this repo's `tsconfig.json` has `"include": ["src"]`, so it never type-checks `server.ts` or anything under `lib/`. The break only surfaced as a live `ReferenceError: safeProjectId is not defined` crashing the dev server under real load (reproduced by firing the sidebar's real ~184-parallel-project session-list request burst directly at a manually-run server so the crash log could be captured). Fixed by restoring the exact original non-iOS helpers from git history. **Lesson recorded for future backend edits in this repo: `tsc` here only proves the frontend compiles — server-side changes must be verified by actually running the server, not by a clean `tsc` result.**
- **[LIVE_PASS]** Re-verified after the fix: `/api/vibe/projects`, `/api/opencode/sessions/:projectId` (fired all ~184 in parallel), `/api/opencode/start` (real project + git init + session + prompt), `/api/vibe/projects/import`, and `/api/vibe/projects/:id/open-folder` all confirmed working via direct requests against a live server; the actual Vibe Coder UI was then loaded fresh in a browser tab with zero console errors and the server still healthy afterward.
- **[LIVE_PASS]** Welcome page: the "iOS app" quick-start tile was replaced with "API / Backend" (`Build me a backend API service`) — a suitable, distinct third build target that needs no new preview infrastructure. Verified live: clicking it fills the composer correctly. The platform-ambiguity question ("Which platform should I target?") now only offers Website/Desktop app.
- `npm run build` (client + server) and `tsc --noEmit` both clean after the fix.

## P1 — Must fix

1. **[FIXED this session]** Screen Companion — fully built, real backend (confirmed via a passing test that included a genuine Gemini vision call) — had **zero discoverable UI entry point**. No launcher tile, no slash command, no shortcut. Verified live: opens correctly, correctly reports "Electron required for overlay" in web mode (honest platform-limitation messaging, not a fake capability claim).

2. **[FIXED this session]** Screen Companion's `ask()` fallback echoed a hardcoded placeholder sentence back to the user as if it were a real answer, whenever the LLM path was unavailable (confirmed trigger: DeepSeek `402 Insufficient Balance` on this account). Asking "what is 2+2" returned "User is asking about their current screen via Clyra Companion..." — a non-sequitur, not an answer and not an honest "I can't answer that right now" either. Root cause: the frontend sent a descriptive placeholder string as `visionSummary` when no real screen context existed, and the server's offline-fallback heuristic (`length > 40 chars` = "trust this as real vision content") got fooled by it. Fixed in `ScreenCompanionWorkspace.tsx` — only send `visionSummary` when a real one exists; verified the corrected empty-string payload now gets the server's honest generic fallback instead.

3. **[FIXED]** AI Clipper: rapid double-clicking "Generate clips" fired two real `POST /api/clipper/start` pipeline runs. Fixed with a synchronous `starting` ref guard in `AIClipper.tsx`'s `run()` (React state alone lags a render behind the click). `tsc`/build clean.

4. **[FIXED — Screen Companion remaster]** The native floating overlay (`electron/companion.html`, loaded by `companion-manager.mjs`) was a permanently-expanded 400×620 glass chat panel with emoji icons and no Clyra blob identity — not the compact Glaido-style bar the product calls for. Remastered while explicitly preserving all existing backend/IPC (`companion:ask/see/startGuide/startControl/takeManualControl/resumeAi/stopControl`, real `res.on(...)`-based cursor/vision pipeline — untouched):
   - Window now opens **collapsed** (420×64, bottom-centre of whichever display has the cursor — was previously bottom-right of the primary display only) and **expands to 420×560 on demand** via new `companion:expand`/`companion:collapse` IPC (native `setBounds` with the bottom edge held fixed, so it grows upward, not downward off-screen). Position is remembered across sessions (`lastBounds`, persisted on the window's own `moved` event).
   - Replaced the emoji command-tab (📷🎙◎◉) with a real blob — a genuine Clyra-identity SVG anchor (not the full animated engine, which is a complex React/framer-motion system not worth risky vanilla-JS reimplementation) with real CSS-driven states: `idle` (breathing), `listening` (driven by **real** mic amplitude via `getUserMedia` + `AnalyserNode`, not a fake loop), `capturing` (one ripple on screen-capture), `thinking`, `speaking` (procedural pulse — the Web Speech API exposes no real synthesis amplitude, so this is an honest approximation, not a fabricated "real amplitude" claim), `controlling` (a distinct restrained ring), `error` (one subtle desaturation flash, no red flashing).
   - Guide/Control triggers preserved, relocated into the expanded panel's header (the "quiet overflow" the spec calls for) rather than cluttering the collapsed bar.
   - Context is now shown honestly: a "Screen" chip only appears after a real vision result comes back, never claimed speculatively.
   - Verified live via a local static server (Electron's own `window.clyraCompanion` bridge is naturally absent outside Electron, which correctly triggers the `error` blob state and an honest error message — confirmed this is graceful, not a hang/crash). Collapsed bar, expand morph, message rendering, and header layout at the real 420px width all visually verified via screenshots. `node --check` on all three touched Electron files, `tsc --noEmit`, and full `npm run build` all clean.
   - Not done: real click-through (`setIgnoreMouseEvents`) for the transparent area around the collapsed bar — deferred as a separate, riskier main-process change rather than bolted on unverified; the collapsed bar itself is already far smaller than before (64px vs. 620px tall), which was the primary "giant card" complaint.

8. **[IMPLEMENTED — real gap, not previously built]** Find-in-page had zero frontend UI despite a fully working backend (Electron's native `webContents.findInPage`/`stopFindInPage`, exposed via `/api/openbrowser/find` in both the Electron and Playwright-web backends) — `desktop.browser.find()` existed but was never called from anywhere in the browser workspace. Built a minimal find bar (input + live match counter + close), wired to Cmd+F (both the Electron `onFocusFind` event and a web-mode fallback keydown handler), Enter-to-find-next, and Escape/×-to-close. **Verified LIVE end-to-end**: opened on a real Google page, typed a query, got a genuine live match count back ("1 of 6") from the actual page content — not mocked.
   - Found and fixed a real framer-motion `AnimatePresence` integration bug during this work: wrapping the find bar in `<AnimatePresence><motion.div>...</motion.div></AnimatePresence>` caused `closeFind()` to genuinely execute (confirmed via a temporary diagnostic log — state setter calls fired, `findOpen` was correctly read as `true` at call time) but the exit animation never completed and the bar never actually left the DOM, even after several seconds and via three independent close paths (Escape, `.click()`, and calling the React `onClick` prop directly). Replaced with a plain conditional render (no exit animation) — confirmed fixed immediately, LIVE_PASS. Not investigated further given the fix is correct and low-risk; worth a note that this file has several other `AnimatePresence` regions that were not re-audited for the same class of issue.
